# Requesting YOUNG IN Chromass GC fixtures

- Prepared: 2026-08-16
- Status: local research request; do not attach files to a public issue
- Target: evidence needed to evaluate a future verified Ordifile adapter

Ordifile does not currently support YOUNG IN Chromass native data. The purpose of this
request is to obtain enough lawful, privacy-reviewed material to distinguish completed
chromatograms from temporary or recovery files and to compare native values with an
official export. Receiving a file does not create a support claim.

## Intake status — 2026-08-17

An owner-supplied, local-only archive has partially fulfilled the native-file request.
It contains 23 unique `.prm` completed-chromatogram candidates with YL-Clarity 9.0.1
candidate markers, but no `.raw`, method, sequence, calibration, `.chr`, `.txt`,
`.cdf`, `.asc`, or other official export companion. Ten filenames are FID-labelled,
ten are TCD-labelled, and three remain unclassified; none of those labels is accepted
as native detector evidence.

The remaining minimum request is a privacy-reviewed official `.chr`, `.txt`, or `.cdf`
export from at least one of those exact runs, the matching detector/channel
configuration, and the vendor procedure used to create the export. A multi-detector
claim also requires a confirmed FID+TCD run and its complete multi-signal export. The
local native files remain `ACCEPT_EXTERNAL_ONLY` and must not be attached to Issue #2.

## Minimum useful set

Please preserve each acquisition's original run or project structure. Do not detach a
single result file if the chromatography software creates required sibling files.

| Set | Requested material | Minimum |
|---|---|---:|
| A | Normal completed FID acquisitions | 3 runs |
| B | Normal completed TCD acquisitions | 3 runs |
| C | Acquisitions using both FID and TCD | 3 runs |
| D | Blank, calibration standard, or quality-control acquisition | 1 run |
| E | Official CSV, TXT, or AIA/ANDI export from the same native acquisition | 1 paired run |
| F | Sequence file or project structure needed to interpret run order | 1 complete example |
| G | Method file used by the paired run | 1 complete example |
| H | Calibration file, when the software stores one separately | 1 example if available |

FID-only material is still useful, but it can validate only FID. A ChroZen run cannot
validate YL6500, and one software generation cannot validate another.

## Record separately

Provide a plain-text note that does not contain credentials or license keys:

- exact manufacturer and GC model as shown by the instrument or official software;
- detector configuration and channel names;
- chromatography data system name and exact version;
- operating system version, if relevant to opening the project;
- whether the acquisition completed normally;
- expected acquisition date, run duration, channel count, and sample order;
- the exact vendor procedure used to export CSV, TXT, or AIA/ANDI;
- whether `.prm`, `.raw`, or another file is treated by the software as the completed
  chromatogram, temporary acquisition data, recovery data, processed result, method,
  sequence, calibration, or report;
- whether the same run opens in YL-Clarity and DataApex Clarity, if this was lawfully
  tested through ordinary product functionality;
- confirmation that the provider is authorized to share the files for local open-source
  interoperability research and whether redistribution is permitted.

## Privacy and handling

Before sharing, check filenames and content for personal names, email addresses,
institution or laboratory names, sample identities, serial numbers, license data,
Windows or network paths, hostnames, and free-text notes. Do not publish files in a
GitHub issue, pull request, release, chat transcript, or public cloud link.

The project owner should place the material only under one of these ignored local
paths:

```text
.external-fixtures/youngin/
.research-downloads/youngin/
```

Keep an unchanged original copy read-only. If redaction is necessary, work on a second
copy, record every changed field and byte-level output digest, and never alter signal
values. Binary metadata must not be edited unless the format can be regenerated by the
vendor software and the effect is understood. A privacy-clean export is not a
replacement for the original native fixture when testing a native reader.

For each received artifact, record:

```text
source or provider authorization
received date
original filename or run root
file count and total size
SHA-256 for the archive and selected files
software and instrument versions
privacy review result
redistribution decision
official export pairing
expected signal and metadata summary
```

Unless redistribution is explicitly verified, classify the fixture as
`ACCEPT_EXTERNAL_ONLY`. Local access does not authorize committing the data.

## Acceptance criteria for implementation use

A future adapter can use this fixture set only after all of the following are true:

- at least one completed acquisition can be distinguished from temporary/recovery
  files by internal evidence and required siblings;
- the software generation and internal format version are known;
- FID or TCD signal point count, time range, channel labels, and units can be extracted
  without a vendor DLL or access-control bypass;
- the native result agrees with an official export under a documented numeric policy;
- malformed, incomplete, and unsupported-version examples produce bounded structured
  failures;
- license, provider authorization, trademark wording, and privacy have been reviewed;
- the minimum verified fixture quantity in the investigation document is met.
