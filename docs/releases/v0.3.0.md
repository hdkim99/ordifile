# Ordifile v0.3.0 — Cross-vendor peak results in one workbook

Ordifile v0.3.0 is the first result-first cross-vendor release. It adds two
narrowly bounded Experimental result adapters that convert explicit retention time and
peak area rows into the same canonical workbook, while keeping raw readers independent.

## Highlights

- Adds an Experimental Agilent ChemStation Result XML adapter for the exact
  `C.01.10 [201]`, single `FID1/A`, `Percent`/`Area` profile.
- Adds an Experimental Shimadzu LabSolutions Result ASCII adapter for the exact 5.82,
  GC-2014, single `SFID1` / `Ch1` profile.
- Converts a supported result export without requiring its native raw file.
- Adds the manufacturer-neutral `Peak_Order_Matrix` for source-order RT/area pairs.
- Adds an Experimental YoungIn YL-Clarity `.PRM` structural reader for one observed
  `9.0.1.19` profile. It does not provide YoungIn result RT or area.
- Retains the Experimental Agilent `.CH` v181, Shimadzu LabSolutions `.GCD`, and
  Shimadzu GCMSsolution `.QGD` raw/chromatogram capabilities from v0.2.1.

Controlled external validation combined 36 Agilent result rows and 83 Shimadzu result
rows into one workbook: 119 `Peaks` rows and two independent `Peak_Order_Matrix`
streams. The workbook reopened successfully, and privacy-bearing source basenames were
not exposed.

## Result-first workbook output

Each exact result adapter maps source rows through the same path:

```text
exact vendor Result Adapter
  -> canonical PeakRecord
  -> Peaks / Peak_Order_Matrix / Peak_Matrix
  -> one Excel workbook
```

`Peaks` is the common long-form result table. `Peak_Order_Matrix` preserves original
observation order as atomic RT/area pairs together with manufacturer, detector,
channel, RT-unit, and area-unit provenance. The existing `Peak_Matrix` remains an
explicit-compound area matrix; Ordifile does not infer compound identity from similar
retention times.

Raw adapters remain optional, independent capabilities. Mixed raw and result inputs
are processed per file, so a supported result export can produce peaks without a raw
sibling and supported raw inputs can still contribute signal or structural-record
sheets.

## Exact Experimental boundaries

| Adapter | Exact tested profile | Result or signal output | Explicitly unsupported |
|---|---|---|---|
| Agilent ChemStation Result XML | `C.01.10 [201]`, one `FID1/A`, `Percent`/`Area` | observed RT `min`, Area `pA*s`, Height `pA`, integration start/end, observation order, non-empty calibrated compound names | other revisions, multiple signals/detectors, other quantitation modes, raw data, automatic raw pairing |
| Shimadzu LabSolutions Result ASCII | 5.82 `Data File`, GC-2014, one `SFID1` / `Ch1` | Peak#, RT/start/end `min`, raw Area and Height values, observation order | other versions/instruments/channels, physical Area/Height units, compound identity for the tested blank-ID profile, raw data, automatic raw pairing |
| YoungIn YL-Clarity `.PRM` | observed `9.0.1.19` structural profile | ordered stored binary32 records and allowlisted stored labels | RT, area, peaks, time axis, scaling, physical unit, verified detector semantics |
| Agilent ChemStation `.CH` | internal v181 exact GC-FID profile | structural record index and raw integer | RT, scaling, physical unit, peak results, other versions |
| Shimadzu LabSolutions `.GCD` | 5.82, GC-2014, single `SFID1` | chromatogram RT `min` and signal `uV` | peak results and untested profiles |
| Shimadzu GCMSsolution `.QGD` | exact File Property `4.00` TIC profile | RT `min` and native TIC integer | physical TIC unit, scientific MS1/m/z export, identification, quantitation |

These are exact-profile compatibility statements, not umbrella support claims for a
manufacturer, product family, or file extension.

## Units and cross-vendor comparisons

- Agilent Result Area retains the explicit source unit `pA*s`; Height retains `pA`.
- Shimadzu Result Area and Height preserve numeric source values, but their physical
  units remain unknown.
- Shimadzu `.GCD` signal uses the verified source unit `uV`.
- Shimadzu `.QGD` TIC and YoungIn structural records have no verified physical unit.
- Ordifile does not normalize or directly equate areas with different or unknown units.
- Similar retention times are not used to merge peaks or invent compound identity.

## Privacy, fixture, and license boundaries

- Privacy-sensitive vendor sources use a content-derived public SHA-256 identity;
  private basenames, paths, operators, sample identities, and privacy-bearing or
  non-allowlisted instrument/run metadata are excluded from public workbook and
  diagnostic surfaces. Allowlisted structural profile metadata remains available.
- The external Agilent Result XML fixture is controlled under its upstream CeCILL-2.1
  repository boundary. The external Shimadzu Result ASCII fixture is controlled under
  its upstream repository-level GPL >= 3 boundary, with no file-specific notice found.
- External validation fixtures are not runtime dependencies and are not committed,
  bundled, uploaded as workflow artifacts, or included in release distributions.
- No proprietary, GPL, LGPL, or CeCILL implementation code is copied or translated
  into Ordifile. Ordifile remains Apache-2.0 licensed.

## Installation

After the v0.3.0 tag workflow completes successfully, install the exact release from
PyPI in a clean Python 3.11–3.14 environment:

```bash
python -m pip install --no-cache-dir ordifile==0.3.0
ordifile --version
ordifile formats
```

## Upgrade notes

This is a backward-compatible minor release. Existing verified generic CSV, TSV, TXT,
and XLSX schemas and the existing compound `Peak_Matrix` behavior remain unchanged.
The new result adapters and all proprietary raw readers remain Experimental and reject
profiles outside their exact tested boundaries. Applications should inspect adapter
status and structured warnings instead of assuming every file with a matching suffix
is supported.

YoungIn result RT/area conversion remains pending an actual YL-Clarity Export Data or
`export_results` fixture. A future result adapter will remain independent of the merged
PRM structural reader.

## Checksums and provenance
